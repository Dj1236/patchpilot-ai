Bug report in. Tested patch out. Brakes built in.

PatchPilot AI is an autonomous repair agent for approved Python repositories. The model only reads and proposes. Allowlists, patch rules, budgets, a locked-down sandbox, hidden-test grading and a human approval gate are enforced in code outside it.

the workflow · seven scenes

Generating a patch is the easy part. Trusting it is the work.

  1. 01 · the problem

    A bug report arrives.

    Issue text is untrusted input. A plausible change can be written in seconds, but plausible is not correct, and the repository itself may be hostile.

  2. 02 · investigation

    Read a pinned snapshot, never a live checkout.

    The repository must be on an allowlist. Its commit is pinned and read from git objects. The model explores with four read-only tools and no shell.

  3. 03 · first proposal

    One fix, one regression test.

    Edits are search-and-replace and must match exactly once. PatchPilot applies them and computes the diff itself. This one touches the right method and changes nothing that matters.

  4. 04 · failure

    The sandbox rejects it.

    Both versions run in a container with no network and no credentials. The new test fails before the patch, as it should, and still fails after it. Not verified.

  5. 05 · repair

    Feedback from its own checks, within a budget.

    In repair mode the model is told what its visible checks found, nothing from hidden tests, and tries again. At most five proposals, three by default, each applied to the original files.

  6. 06 · verification

    Verified by the agent. Then judged by someone else.

    The agent’s checks give only candidate_verified. After the run, hidden tests the agent never saw are added to a tree rebuilt from the pinned start. Only they decide resolved.

  7. 07 · human approval

    A person, not the agent, authorizes the write.

    The proposal shows every changed file in full. A person approves it by typing the start of its patch digest. Only then can one draft pull request be opened. Nothing is ever merged.

    engineering

    Every safety property is code, and every control has a test.

    The values below are the defaults in code. The security tests attack a real container, not configuration flags.

    01 · containment

    Sandbox isolation

    Repository code, including the candidate’s tests, runs only in a container. The host never imports or executes it, and test commands come from the task manifest, never from model output.

    • Network, writes outside the workspace, privilege, resource limits and leftover processes are attacked by tests in a real container
    • The container shares the host kernel
    • Tests can forge their own results in the same process (kept as a known, expected failure)

    02 · bounds

    Tool boundaries, patch rules and budgets

    The model gets four read-only tools and no shell. Paths are confined to the snapshot. Proposals are checked against the patch policy before anything runs. Every loop has a ceiling, enforced outside the model.

    03 · memory

    Feedback, retries, checkpoints and resume

    The repair loop is plain functions over a small JSON state machine. State is saved before every model request and after every step. A resume is refused if the spend ledger shows any request after the checkpoint, so a request whose outcome is unknown is never repeated.

    • JSON with a schema version, a SHA-256 over the state, atomic replace and fsync, 16 MB at most
    • Limits and counters are restored, so restarting cannot reset a budget
    • Resume is offline only for now, replaying recorded answers

    04 · separation

    Hidden-test evaluation and secret redaction

    Hidden tests never enter the agent’s files, images or prompts; tests check every message sent. Known secret values are replaced before anything is written to traces, reports, checkpoints or proposals. Raw traces stay local.

    05 · consent

    Approval binding and failure handling

    Only patchpilot approve creates an approval, and only when a person types the start of the patch digest. It is bound to the whole proposal, expires after 24 hours, and covers one draft PR. Try the same check here; nothing is sent.

    What “resolved” means

    After the run ends, grade_candidate rebuilds the tree from the pinned start, adds the hidden tests last, and requires every fail-to-pass test to pass and every pass-to-pass test to keep passing. The agent never sees these tests, and the result is never fed back.

    Limits

    • Four synthetic tasks written for this project; no real open-source bugs yet
    • Answers scripted by the same developer who wrote the tasks; one deterministic run each
    • The live comparison with a real model is pending
